# Local-first workflow features

Swiftspring does not use a Mailspring ID, feature quota, billing endpoint, or
Mailspring-hosted metadata service. Workflow state is stored in the local GRDB
database and scheduled work is processed while the app is running or during an
OS-granted background refresh.

## Local features

- Mail templates
- Scheduled sends
- Snoozed conversations
- Follow-up reminders
- Contact history collected from mail
- Activity events generated by local scheduling and reminders

A scheduled message is sent at its target time when the device is awake. If the
device is asleep or offline, it remains queued and is delivered the next time
Swiftspring gets to run. This is intentional: the app does not hand mail to a
vendor server to obtain always-on delivery.

## Self-hosted gateway features

Read receipts, link tracking, and public conversation sharing require an HTTPS
address that recipients can reach. `localhost` cannot provide those features:
it only refers to the recipient's own device. The app therefore treats them as
an optional self-hosted gateway configuration, and rejects loopback URLs.

The gateway must be operated by the user, reachable over public HTTPS, and
implement authenticated event ingestion plus public tracking/share routes. Its
credentials must be stored in the platform keychain; the local database stores
only the public base URL and enabled capabilities.

## Local language services

Grammar checking and translation can be provided by a local LanguageTool and a
local translation model/service. They are intentionally separate adapters so a
deployment can choose its language coverage and model size without sending mail
content to a vendor. A bundled adapter should only accept loopback URLs unless
the user explicitly opts into another provider.
